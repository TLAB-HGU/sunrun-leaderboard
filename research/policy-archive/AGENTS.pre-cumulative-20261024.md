- `$P register --direction D3 --owner worker-3 --hypothesis "<failure mode + mechanism>" --cmd "<command>" --code <files> --reference E0001 --kind pilot|full|final --experience X0004 X0009`

  from a real future-poison test (exact keys, positive control). Candidates to freeze also write `predictions_official.parquet`
  (fit on targets < 2026-05-29). Template: `leaderboard/experiments/expos_runners/existing_all.py`.

- `$P freeze E0007 [--final E0009]` then `$P official-score` — exactly once, only for a gate-passing, reviewed, clean candidate.
- Experience: `$P exp-query --text "<english keywords>" --tags image negative`; `$P exp-add --record <path|Exxxx> --applicability .. --finding .. --implication .. --tags .. --author ..`

### GPUs, parallelism and pipelining (user directive 2026-10-05: use BOTH GPUs)
- `--gpu` now picks the least-loaded free GPU (0 or 1). `--prefer-gpu 1` targets GPU1, and `--gpus 2` holds both
  (`$CUDA_VISIBLE_DEVICES`/`$EXPOS_GPUS`="0,1") for data-parallel training or sharded extraction.
  `$P run E00xx --background` starts a run detached, so several runs can go at once. `$P board` marks RUNNING jobs with their GPU.
- Keep both GPUs busy: at most one GPU job per GPU at a time, and fill GPU1 before queueing a second job on GPU0.
  Keep the sum of CPU `n_jobs` across concurrent runs of ALL sun sessions (sun-gjc + sun-fm) at 10 or less
  (2026-10-11 user CPU split: power_forecast uses up to 12 of the 24 cores). This overrides every "n_jobs <= 10 (all sun sessions; 2026-10-11 CPU split)" below.
  GPU1 stays sunrun's; power_forecast may borrow it only while the expos gpu1.lock is free, with jobs <= 25 min,
  so an expos lease waits at most ~25 min. GPU0 belongs to power_forecast.
- **Device by model family (user directive 2026-10-11 19:55 KST, authoritative; overrides any line in this file that puts
  boosting on cuda or a neural model on CPU):** boosting/tree/tabular models (XGBoost, LightGBM, CatBoost, RF, ridge/kNN and
  other sklearn) run on CPU only (`device="cpu"`, within the n_jobs <= 10 cap). Deep-learning models (torch time-series/image
  nets, DINOv3/feature extraction, pretrained/foundation models incl. TabPFN/Kumo) run on GPU via `expos run --gpu
  --prefer-gpu 1` (GPU1; GPU0 is power_forecast's). A DL run on CPU is allowed only when no GPU lease can be had and must be
  recorded with its device; prefer waiting for the lease. Do not move running jobs; apply to new registrations. Same-device
  matching applies only within a model family (reruns/variants of the same recipe; XGB CPU vs cuda differ by ~85 MSE, see
  E0368 note). A cross-family comparison (GPU neural candidate vs the frozen CPU XGB baseline such as E0472/E0368) uses the
  frozen baseline as is; record both devices.
- Parallelise inside runners:
  - The three period fits (dev/selection/audit) are independent: run them in parallel processes (XGBoost stays on CPU).
  - Seed replicates and pilots of different directions run in parallel.
- Pipeline stages:
  - Expensive features (SUVI strips, DINOv3 patch tokens, longitude maps) are computed once into a hash-keyed cache under
    `leaderboard/store/<feature>-cache/` and reused.
  - Extract the next experiment's features on one GPU while the current one trains on the other.
  - Shard large extractions across both GPUs by image index.
- Causality, poison tests and identical rows still apply to every parallel or cached path. A cache key must include the code
  and input hashes.

### Search policy from autoresearch literature (user directive 2026-10-05)
Sources: arXiv 2609.30541 (AutoResearch at production scale), 2605.13874 (GEAR), 2606.25198 (Heuresis),
2609.25047 (AIBuildAI-2.5).
- **Multi-objective, no metric fixation**: before every decision run `$P pareto`.
  - It shows the non-dominated front vs E0003 on (mean relative MSE, pooled F1) and the elites of each niche
    (niche = top lineage x kind).
  - Reviewers judge both objectives. The adoption bar is unchanged.
- **Crossover quota (GEAR)**: each cycle registers at least one experiment that combines two front or elite parents from
  different niches or opposite ends of the front.
  - Example: MSE elite E0074/E0063 x F1 elite E0060/E0052.
  - Name both parent ids in the hypothesis and say which component comes from which parent.
- **Go-Explore revisit (Heuresis)**: a pilot that looked good but shrank at full density (E0074 -1.65% -> E0077 -0.46%,
  E0059, E0085) is a stepping stone.
  - Diagnose why the gain shrank (grid density, train rows, alpha selection) and record it with `exp-add`.
  - Restart from it rather than discarding it.
- **Pre-run review (AIBuildAI)**: before a full run a critic scores expected improvement, grounding (experience ids) and
  feasibility from 1 to 5. If the mean is below 3, only a pilot is allowed.
- **Prevent infrastructure failures**:
  - A new runner must pass a smoke run (`EXPOS_SMOKE=1`, reduced rows, about 1 minute) before `$P run`.
  - `$P board` shows the rc!=0 count over the last 20 runs and marks dead runs STALE. Record the cause of each and clean up.
- Novelty for its own sake is not a goal: Heuresis found novel ideas rarely reach top quality. Diversity serves the front.

### Roles (gjc subagents; all muse-spark 1.3 xhigh via ~/.gjc/agent/config.yml)
- Main (this session): owns the direction DAG, assigns tasks, reads Reviewer reports, decides continue/verify/branch/revise,
  freezes. Main does not write experiment code itself when a Worker can.
- Worker = `executor` subagent: owns its experiments end-to-end (code in `leaderboard/experiments/<direction_slug>/`, tests in
  `leaderboard/tests/`), registers/runs/evaluates through expos, reports ids + numbers. At most 3 Workers at once; GPU jobs
  use `--gpu` (two A5000 leases, shared with other sessions).
- Reviewer = `critic` subagent, read-only: audits assigned experiment ids against raw receipts (graph line, logs, predictions,
  poison.json, code diff), checks protocol violations and overclaims, writes `expos review`. Never reviews its own work.

### Loop (EEM decision protocol)
1. Before any new experiment: `exp-query` for the direction. If lessons already answer it, decide (pursue/revise/reject) and cite ids.
2. If knowledge is missing, run a bounded pilot (`--kind pilot`, <=10 min or one period on a 6h grid) aimed only at that gap.
3. Full experiment -> evaluate -> Reviewer -> Main decision -> `exp-add` lessons (positive and negative) -> next task.
4. Keep `research/BACKLOG.md` with >= 6 ranked candidate experiments; take the top distinct ones when Workers free up.

### Anti-stall
- Idle GPUs with no running experiment is a defect: register the next experiment instead of writing notes.
- No re-verification of verified results, no audit-only turns, no "nothing to do" reports while the backlog is non-empty.
- A closed direction is closed only for the exact mechanism tested. Fishing = choosing configs with official truth or re-running
  an identical registered config; a new preregistered hypothesis is never fishing.

### Reporting
- Korean, concise progress lines. After each Main decision append one line to `research/PROGRESS.md`
  (time, direction, experiment ids, 3-period numbers, decision).
- Report unmet honestly. Complete the goal only after `official-score` shows achieved=true.
